# 16 · dsh 0.1.5-rc.2 适配

> 2026-09-15。dsh 从 0.1.1-rc.2 跨三个版本线升到 0.1.5-rc.2（官方 0.1.2 起
> Web 界面网络访问启用一次性 token 认证），本插件同步适配。**0.1.1 旧运行时
> 保持兼容（双路径设计）。**

## 背景

- dsh 0.1.2-rc.1（2026-09-03）发布说明：「网络访问 Web 界面时启用链接中的
  一次性 token 认证鉴权」——内网暴露的原始痛点由官方收口。
- 本插件原依赖的三个契约在 0.1.5 全部变动，升级后首次启动即崩
  （`plugin tree failed to load: failed to apply loader entry input-assist`）。
- 参考了社区 [dsh-plugin-upgrade-skill](https://github.com/oh-my-dsh/dsh-plugin-upgrade-skill)
  的逐版本迁移卡片（其「六插件零改动跨 0.1.3→0.1.5」结论对纯 UI 插件成立；
  本插件因 host 半边 RPC 注册而命中了更深的坑）。

## 三处契约变更与适配

### 1 · cordis 服务注入收紧：loader 入口加 `webServer`

- **症状**：`cannot get property "webServer" without inject`。
- **原因**：0.1.5 的 `connection.rpc.handle()` 注册路由时经
  `owner.webServer`（owner = 调用方插件的 ctx），cordis 4 要求访问的服务
  必须在 loader 入口的 `inject` 列表里声明。
- **适配**：`cordis.patch.yml` 的 insert 行
  `inject: [connection]` → `inject: [connection, webServer]`。

### 2 · `@deepseek-ai/dsh-client-runtime` 包消亡

- **症状**：npm 上该包止步 0.1.1-rc.2；0.1.5 树里没有。`createSnapshotStore`
  迁去了 `@deepseek-ai/dsh-client-store`——但后者**不在** web-app 的 loader
  行里，浏览器 ModuleLoader 不保证提供，不能作为 external 依赖。
- **适配**：收编。我们只用了 `getSnapshot / set / subscribe` 三个方法
  （选择器 hook 本来就由宿主 ui-renderer 从 `ObservableSnapshot` 合成，
  契约是结构化的），新增 `src/snapshot-store.ts` 15 行实现打进 client
  bundle（`tsdown.config.ts` 去掉该 external；`dsh.client.inject` 与
  devDeps 移除该包；bundle 守卫测试改为断言 store 已打包、无残留 require）。
  从此不再依赖宿主 roster 的包名变动。

### 3 · `connection.rpc.handle()` 上游回归 → RPC over fetch

- **症状**：inject 修好后仍在 `client-connection` 内部同一处抛
  `cannot get property "webServer" without inject`。
- **根因**（读 cordis 4 源码定位）：service 的 traceable 代理把「读取方
  ctx」经 `ctx.extend({shadow: 服务原始 ctx})` 传入 `get rpc()`；此后
  `owner.webServer` 的服务解析从 shadow 指向的 **connection 插件自己的
  fiber 链**起向上走，而 webServer 是 connection 在自己的
  `ctx.inject(['webServer'])` **子 fiber** 里拿到的——永远解析不到。
  官方包自身只走 `rpc.intercept` / `fetch.register` 两条内存表路径
  （`dsh-api-gateway` 用前者，`dsh-client-file-upload` 用后者），
  `rpc.handle` 的路由注册路径对第三方 host 插件在 0.1.5-rc.2 不可用
  （上游回归，待报告）。
- **适配**：host 半边按 `connection.fetch` 是否存在分流——
  - **0.1.5+**：RPC 挂 `connection.fetch` 精确路由
    `/api/input-assist/rpc`（body `{endpoint, payload}` → `RpcResult`
    JSON，`createRpcFetchHandler` 复用既有 handler 纯函数），流式路由
    照旧 `/api/input-assist/stream`。两者都只进内存表，不触 webServer，
    自动继承 Host/Origin/browserAuth 鉴权栅栏。
  - **≤0.1.1-rc.2**：保留 `rpc.handle` 原路径（旧实现注册不触
    webServer，一直正常）+ webServer exact 路由流式兜底。
  - 浏览器半边 `rpc()`：先打 fetch 路由，404（旧运行时）自动回退
    `connection.rpc.call` 旧通道，一次往返的差异仅存在于旧运行时。
- **附带**：`ctx.get('connection')` 改为属性访问 `ctx.connection`
  （`get()` 返回的 traceable 绑定的是根 ctx）；dsh-settings 的
  `settingsNamespace()` 帮助函数移除，`register(NS, schema)` 直接收
  字符串（side-effect import 保留 cordis Context 的 settings 服务类型声明）。

## 验证（2026-09-15，本机 macOS）

- `npm test`：116/116 全绿（typecheck 打在 0.1.5-rc.2 契约类型上）。
- 真机 curl 冒烟（dsh 0.1.5-rc.2，`--profile web --no-open`）：
  - `GET /?token=…` 303 建会话 ✓；无凭证打 API **401**（新认证生效）✓
  - `POST /api/input-assist/rpc` `config.get` 返回完整配置 ✓
  - `POST /api/input-assist/stream` 回 SSE 帧 ✓；`cancel` 端点 ✓
  - 客户端 combo（11.2MB）含 `id:"dsh-input-assist",factory` 模块 ✓
- 浏览器交互层（ghost 渐显、设置卡片、词库编辑器）待日常使用回归。

## 依赖变化

- devDeps：`@deepseek-ai/cordis` ^4.0.2；移除 `@deepseek-ai/dsh-client-runtime`
- deps：`@deepseek-ai/dsh-settings` ^0.1.5-rc.2；`@deepseek-ai/schemastery`
  ^3.18.2（dsh-settings 0.1.5 的 peer 要求，原锁 3.18.1 触发 ERESOLVE）

  package-lock.json` 干净重装解决
