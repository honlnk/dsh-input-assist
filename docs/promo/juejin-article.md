# 智能体的眼睛还没睁开：它读不懂你打错的字——我给 dsh 的输入框做了校对和补全

> 摘要（约 100 字）：「错词」打成「措辞」，人看不出来，模型也不会问——它只会照着错的指令信心十足地执行。Agent 时代，输入框是编程接口，纠错比补全更要紧。聊聊这个被忽视的问题，以及我给 dsh 做的开源输入助手：双层错别字检查 + Copilot 式补全。

先做个小实验。打开你常用的智能体（Claude Code、Codex、Cursor 都行），输入框里敲这句：

> 这份更新公告下午三点要发给全部用户，时间紧，你帮我把里面的措辞全部改掉，改完直接定稿，别的都不用动

然后停住，看一眼。有什么问题吗？没有——任务清楚、要求具体、语法通顺，「措辞」是个正经词，任何拼写检查都不会标它。

现在告诉你：我本来想打的是「**错词**」。cuò cí，拼音一模一样，输入法递错了词。

回想一下：你刚才读那句话的时候，脑子里有过一丝怀疑吗？没有。模型也不会有。于是你只想让它挑出几个错别字，它收到的指令却是「把公告的措辞全部重写、直接定稿」——它会兢兢业业地把每句话都换个说法，每一处单看都合情合理，但没有一处是你想要的。运气好，你 review 时发现方向从一开始就错了，三点的 deadline 废在返工上；运气不好，你没细看就发了——下午三点，全用户收到的不是你写的那份公告。

这样的同音雷一抓一大把，全是打工人天天敲的词：

- 「弃用」打成「启用」（qì yòng / qǐ yòng，只差一个声调）——本想让它把实验功能关掉，它反手给你打开了
- 「中止」打成「终止」（zhōng zhǐ，同音）——一个是「先停一下，还能续」，一个是「杀了吧，不用留了」
- 「实时」打成「适时」（shí shí / shì shí，只差一个声调）——同步策略，一个要毫秒级，一个是「你看着办」
- 「定金」打成「订金」（dìng jīn，同音）——写进合同里，一个退不了，一个能退

而且这些雷可以在一句话里连环埋。再看这句运维指令：

> 实验功能先启用跑两天看看，旧接口保留到月底；有报错先记录，必要时终止服务，明早我来确认

通顺吗？非常通顺——每个词都是正经词，你一口气就读完了。但如果我本来想打的是「先**弃用**」「必要时**中止**」，这就是两个被反转的指令：它不仅会把你想关的功能打开，还会在该「暂停观察」的时候直接把服务杀掉。两个同音词，两处意思反转，而它每一处都会执行得信心满满。

模型有时能靠上下文猜中你的本意，但这种同音词，两种理解往往都完全说得通，猜中的把握并不大；就算猜中，也只是「猜」，你永远不会知道它哪次猜错。而一个词的偏差，对 Agent 来说不是「看着难受」，是**整个任务跑错方向**——它不会问你，会直接动手。

第一个例子不是我编的。就在写这篇文章的时候，我把「错词」打成了「措辞」，眼睛扫过去两遍都没发现——这类错最阴险的地方在于，**错出来的词本身是对的**，它不在任何错别字词典里，只能靠上下文识别。

当然，错字也不全都这么难缠。「迫不及待」打成「迫不急待」、「receive」打成「recieve」——这种明眼一看就是错的传统错字，反而最省心：错得明明白白，本地词典一查一个准，连模型都不用惊动。难的一直是上面那种：词本身没错，错的只有意思。

Copilot 时代我们早就习惯了编辑器「管」输入：续写靠补全，错字靠波浪线。到了 Agent 时代，输入框从编辑器退化成了聊天框，这两样东西一起消失了。可吊诡的是——**输入框承担的角色反而更重了**：它不再是聊天，是编程接口。你给 Agent 的每句话都是指令，指令里的每个错字、每处歧义，都会原样变成它的行动依据。

这篇文章讲的就是这件事的两半：**纠错为什么比续写更要紧**（以及为什么它被整个行业无视），以及我给 DeepSeek Harness（dsh）做的输入助手插件 [dsh-input-assist](https://github.com/honlnk/dsh-input-assist)，是怎么把这两样都补上的。

## 为什么错字在 Agent 时代变得致命

聊天时代，错字是个礼貌问题：对方看懂了，心照不宣，翻篇。Agent 时代，错字是个**正确性问题**——因为语义理解的最终解释权不在你，在模型。

三类真实的代价：

**① 模型被错字带偏，你还不知道。** 你打「在帮我检查一下」，Agent 理解为「正在帮我检查一下」——它默认你是对的，沉默执行。LLM 有极强的纠错自信，它假设用户永远是对的，于是错别字被静默吞掉，变成一个语义偏移、而你毫无察觉。你得到的回复可能方向就不对，而你以为模型「没理解我的意思」。

**② 技术名词的错拼直接撞墙。** `recieve`、`deprecate` 打成 `depricate`、配置文件名打错——这类错误不再是「看着难受」，是 grep 失败、API 报 404、文件找不到。Agent 会按你写的字面去找，浪费的是轮次、上下文窗口和钱。

**③ 混排场景的隐形滑坡。** 中文用户写 prompt 时中英混排是常态：「把 error handler 改成在 catch 里上报」。在/再、的/得/地、英文单词拼写，错在任何一个都可能改变指令的指向。打字越快，这种错越多；而 Agent 的使用者恰恰是在高频打字。

为什么没人管？三层原因：

1. **认知惯性**：输入框在所有人心里还是「聊天框」，没人把它当编程接口来打磨
2. **LLM 的纠错自信**：模型「能看懂」让所有人误以为「没必要检查」——但「看懂大概」和「理解准确」是两回事
3. **中文语境没人管**：主流工具都在英文世界打磨，在/再、的/得/地这类问题连被提起的资格都没有

## 所以我做了什么

[dsh-input-assist](https://github.com/honlnk/dsh-input-assist)，给 dsh 的输入框装上一个「清醒的眼」：

```shell
dsh plugin --profile web add dsh-input-assist
dsh --profile web
```

两个能力，一守一攻：

**守：双层错别字检查。** 词典层完全跑在浏览器本地——228 条中文错词 + 211 条英文错拼/专名大小写 + 上下文规则，停笔 200ms 即时标红，离线可用，一分钱不花；LLM 层管词典管不了的上下文问题（在/再、的/得/地、英文语境拼写），800ms 防抖。错字用红色波浪线**标在文中**（不是弹窗、不是侧边栏），导航条逐条过，`Ctrl+Shift+F` 一键修当前项——**绝不全量替换**，每一处改动你看得见、你决定。代码块和 URL 永不标记，`camelCase`、`snake_case`、`obj.method` 这类标识符不会误报。

<!-- GIF 占位：错字场景——打字 → 迫不急待 标红 → 导航条提示 → Ctrl+Shift+F 修正 -->

**攻：ghost text 补全。** 停笔 800ms，灰色建议内联出现在光标后（Copilot 同款手感），SSE 流式逐字渐显；`Tab` 逐词采纳（中文按词切分）、`Shift+Tab` 全量、`Esc` 关闭。打字快的人几乎不用等，打字慢的帮你把「继续」「跑一下测试」这类高频句式续出来。中文 IME 组合期一律放行——打拼音时它绝对安静。

纠错是守，补全是攻。一个保证你发出去的指令是对的，一个帮你把指令发得更快。两者加在一起，输入框才从「聊天框」变回「接口」。

## 这两个功能为什么凑得巧

做的时候发现一个有趣的工程事实：补全和纠错可以共用同一条节流和取消管线——停笔 800ms 同时发两路请求（一个 FIM 补全、一个 LLM 校对），打字再动则两路一起取消。互不干扰，还省得各自实现一套防抖。

另一个决定是词典层下沉浏览器。最初的想法是纯 LLM 校对，跑下来发现不对：大部分错字（「迫不急待」「recieve」）是高确定性、低上下文的，为它们烧一次 LLM 调用既慢又贵。拆成两层后：本地词典管确定性的（200ms、零成本、离线），LLM 只管需要上下文的（800ms、与补全同节奏）。各司其职。

## 补全真正有效的两种形态（也是这个插件的下一步）

做完之后对「AI 输入补全什么时候有效」的答案清晰了很多，就两种：**重复的个人模式**（你的高频句式，模型从上下文学，越用越准）和**结构化内容**（路径、命令、技能名——确定性高到不需要 LLM，本地词典零延迟补全，这在 P2 计划里）。

但无论如何，补全是锦上添花；**纠错是雪中送炭**。一个把错的指令拦在发送之前的功能，在 Agent 时代比任何「帮你打字更快」的功能都更本质——因为指令的正确性，直接决定了 Agent 行动的正确性。

## 写在最后

Claude Code、Codex、Cursor 的输入框至今没人管，不是因为技术难，是因为所有人都还把它当聊天框。但 Agent 时代，输入框是你的**唯一控制台**——它值得一个像样的校对，也值得一个像样的补全。
