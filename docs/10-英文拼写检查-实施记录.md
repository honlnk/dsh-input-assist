# 开发记录 · 英文拼写检查

日期：2026-09-12 · 对应 README 状态清单「英文拼写检查」。

## 1. 背景与方案

程序员用户中文里常夹英文（"看看这个 bug 是不是 race condition"），英文错拼
（teh、recieve、defualt）真实高频。方案取舍：

- **做**：高置信错拼词典 + 专名大小写词典（与中文词库同构，零误报可守）；
  LLM 层 prompt 扩展中英混排校对（管词典覆盖不到的长尾与变形）。
- **不做**：通用拼写检查（aspell/hunspell 风格的"词表外即报 + 编辑距离"）——
  技术专名（kubectl、vite）、缩写、变量名全在词表外，误报不可控。

## 2. 实现

### 词典层（本地、零成本）

- **数据**：`data/en-wrong-spellings.txt`（194 条：通用高频错拼 + 程序员词
  错拼 defualt/flase/ture/retrun/stirng…，含 `alot => a lot` 这类修正为
  两词的条目）+ `data/en-proper-nouns.txt`（17 条：github => GitHub、
  typescript => TypeScript…）。收录纪律：错拼/小写形式本身不得是合法英文
  词、缩写或标识符——python/docker/react/windows 等有普通词义的一律不收；
  官方接受小写的（npm、nginx、vscode）不收。
- **扫描**（`scanWithDict` 英文分支）：对掩码后文本跑一次
  `/(?<![\w.])[a-z]+(?![\w.])/g` token 化 + Map 查表。词边界设计一箭三雕：
  - 只匹配**全小写**连续段 → 句首大写、全大写（yelling）天然不查
    （词典层盲区，LLM 层兜底）；
  - 前后紧邻 `\w`（字母/数字/下划线）或 `.` 不匹配 → 驼峰
    `myRecieveFunc`、snake_case `user_recieve`、`obj.recieve`、`utf8xxx`
    一律视为标识符不查；
  - 复用现有 `maskForScan` → 代码块、行内代码、URL 内的英文错拼不检。
- **用户词库**：`mergeDicts` 把 `/^[a-z]+$/` 的用户词条自动分流进英文表——
  用户写 `teh => that` 立即获得词边界匹配，中文词条不受影响；英文自映射
  同样是禁用语义。
- **gen-dict**：读两个英文文件（跨文件查重），英文条目校验错拼全小写
  `[a-z]+`、正词允许单个空格（`a lot`）、长度 ≤24；生成 `EN_PHRASES`。

### LLM 层

- `SYSTEM_PROMPT` 改为中英混排校对器：新增英文拼写与专名大小写检查说明，
  同时明确"变量名/库名/工具名等标识符（含驼峰、下划线写法）不是拼写错误"。
- `isShapedIssue` 的 orig 长度上限 10 → 20（`responsiveness` 14 字符此前
  会被当畸形条目过滤）。

## 3. 验证

- `npm test`：76/76（新增 9：词典层英文检出/中英混排/标识符保护/大写不查/
  未收录不误报/alot 两词修正/代码 URL 掩码；gen-dict 英文校验含空格例外；
  用户词库英文分流；bundle 端到端取 data/ 英文首条验证链路）。
- 真机（dsh web + 本地 link 插件）：英文错拼与专名在输入框标红、导航条
  修正可用（详见会话记录）。

## 4. 遗留

- 词典层只查全小写词：句首大写错拼（Recieve）与变形（recieves）不覆盖，
  由 LLM 层兜底；如变形误漏高频可后续按需补词条。
- 错拼表为手工精选起步（194 条），后续可从公开常见错拼列表批量扩充，
  收录纪律不变。
